# Scholar Harness 开源边界设计

> 开源目标不是“证明透明”，而是降低采用门槛、建立开发者生态并形成事实标准。私有核心也不应等同于“把所有代码藏起来”，而应保护真正决定质量、规模和商业转化的智能与运营系统。

## 1. 当前必须先处理的风险

仓库根目录现已添加统一的专有软件 `LICENSE`，明确当前完整产品仓库不授予复制、修改、分发或商业托管权。部分 `skill-packs/` 和第三方工具仍受其目录内独立许可证约束。若未来拆出公开仓库，还必须继续完成：

1. 为拆出的开源 SDK、schema、CLI 等组件单独选择并附加开源许可证；
2. 第三方依赖、模型、模板、图标和数据集的许可证清单；
3. 贡献者许可协议（CLA）或 Developer Certificate of Origin（DCO）；
4. 开源仓库与商业私有仓库的自动边界检查；
5. 用户数据、密钥、日志、评估样本和商业配置的泄漏扫描。

在这些工作完成前，不应直接把当前整仓库公开。

## 2. 开源原则

1. **开放接入面，保护决策面**：开放格式、SDK、插件协议；保护路由、评估、质量和商业策略。
2. **开放可替换组件，保护复利组件**：解析器可替换；随使用持续改进的证据图谱与工作流质量系统应保护。
3. **用户数据不属于私有核心**：用户拥有并能导出、删除自己的数据；安全保护不等于商业占有。
4. **本地可用，但高级协作与治理收费**：开源版本应能形成真实闭环，不能只是演示壳。
5. **避免 Prompt 迷信**：基础 Prompt 可示例化开放；生产路由、上下文编译、评估策略和动态 Prompt 组合才是私有价值。

## 3. 三层模型

### 3.1 Open Source Layer

目标：获得开发者、降低安全顾虑、建立格式与接口标准。

建议拆出一个干净的 `scholar-harness-core`，而不是公开当前完整产品仓库。

| 能力 | 决策 | 开放范围 | 保留内容 |
|---|---|---|---|
| 数据模型与交换格式 | 开源 | 文献、证据句、主张、产物、工具调用的 schema | 云端内部表、风控字段、商业分析字段 |
| API/SDK | 开源 | 插件、Skill、导入导出、任务状态、资产查询接口 | 私有路由策略与内部服务实现 |
| CLI 工具 | 开源 | 项目初始化、数据校验、包验证、离线导入导出 | 授权、计费、企业部署控制器 |
| 本地运行框架 | 部分开源 | 单用户任务执行、插件沙箱、日志与产物协议 | 生产级多 Agent 路由、质量评分、成本优化与组织治理 |
| Skill 模板 | 开源 | 规范、示例、测试夹具、基础学术任务模板 | 商业高级 Skill、动态装配与优化数据 |
| Agent 模板 | 开源 | 最小可运行示例、工具调用约定 | 生产规划器、失败恢复策略、领域评估器 |
| Prompt | 分层开放 | 教学 Prompt、接口 Prompt、示例 | 生产系统 Prompt、动态上下文编译、风险与质量门禁 |
| Workflow | 部分开源 | 工作流 DSL、示例工作流、开发工具 | 高价值完整流程、组织模板、自动优化策略 |
| 文献解析与转换 | 优先开源 | RIS/Bib/WoS/CNKI 解析、统一模型转换 | 质量纠错规则库与商业数据源适配器可分层 |
| 测试与评估协议 | 开源协议 | 指标定义、兼容性测试、合成样例 | 真实评估集、失败样本、模型得分和权重 |

建议许可证：

- 核心 SDK、schema、CLI：Apache-2.0，兼顾商业采用和专利授权；
- 示例 Skill/模板：Apache-2.0 或 MIT；
- 品牌、商标、官网素材：不随代码许可，单独制定商标政策；
- 若担心云厂商直接托管，可将服务器侧关键组件保留私有，而不是使用模糊的“伪开源”许可证。

### 3.2 Community Layer

目标：把长尾学科需求交给社区，同时建立质量、信任和分发网络。

社区层应“目录开放、运行受控、质量可见”：

- 公共 Skill/插件索引与元数据；
- GitHub 托管的社区包和版本历史；
- 自动兼容性、安全与许可证扫描；
- 发布者身份、签名、评分、安装量和支持状态；
- 学科、期刊、方法、数据源等分类；
- 免费包、付费包和机构私有包并存；
- 社区评审、官方认证和撤回机制；
- 收益分成、退款、恶意包处置和争议处理规则。

社区层不应允许包直接获得任意文件、网络和进程权限。必须使用能力清单、最小权限、安装前提示、运行日志、撤销和隔离执行。

### 3.3 Private Core Layer

目标：保护决定任务成功率、可信度、规模效率和商业化的复利系统。

必须私有：

1. **生产级 Agent 编排**：意图路由、模型选择、上下文预算、工具策略、恢复和降级。
2. **上下文编译器**：从清单、摘要和资产图谱中动态选择最小充分上下文的方法与权重。
3. **证据质量引擎**：候选筛选、重排、支撑度、冲突检测、引用完整性和置信度策略。
4. **PDF Wiki 增强逻辑**：高质量章节/句子/引用映射、证据关系和质量门禁的生产实现。
5. **评估与优化资产**：真实失败样本、接受/退回反馈、基准集、模型表现、回归测试阈值。
6. **组织级知识与权限引擎**：继承、隔离、共享、审计、保留策略和数据治理。
7. **云端商业系统**：身份、按期订阅授权、计费、风控、分销、市场结算和企业控制面。
8. **企业连接器和部署控制面**：SSO、SCIM、KMS、审计导出、私有模型网关、升级和 SLA。
9. **遥测驱动的运营算法**：在明确同意和匿名化前提下形成的成本、性能和质量优化策略。

### 关于数据的准确边界

- 用户文献、PDF、实验数据、草稿、知识库和企业数据：**用户资产，不开源、不训练、不出售，默认本地或按协议托管**。
- 用户可选择贡献的匿名评估反馈：经过明确同意、去标识化和保留期限管理后，才可用于产品优化。
- SH 自建的合成评估集、人工标注规则、基准和模型表现数据：私有核心。
- 公共学术元数据：遵守数据源许可，不因抓取或导入而自动成为 SH 可再分发资产。

## 4. 代码与仓库建议

```text
scholar-harness-core/          Apache-2.0
  schemas/
  sdk/
  cli/
  plugin-runtime-lite/
  importers/
  examples/
  conformance-tests/

scholar-harness-community/     公共目录与社区包
  registry/
  skills/
  plugins/
  templates/

scholar-harness-private/       私有
  orchestration/
  evidence-engine/
  evaluation/
  cloud-control-plane/
  enterprise/
  marketplace-settlement/
```

当前单仓库可以继续开发，但发布时必须由构建清单生成开源镜像，禁止人工复制。

## 5. 开源发布门禁

每次开源发布必须自动检查：

- 无 `.env`、API Key、私钥、用户路径和真实用户数据；
- 无云端商业路由、内部域名、风控规则和生产 Prompt；
- 每个第三方资产有许可证与来源；
- 开放 API 不暴露内部表结构和越权操作；
- 示例数据全部合成或明确允许再分发；
- 插件包有签名、权限清单和可复现构建；
- 开源版本能独立完成一条真实工作流，而不是诱导性空壳。

## 6. 不应开源的错误理由

以下内容不应被误判为壁垒：

- 单个 Prompt；
- 页面 CSS 和普通组件；
- 对公开库的简单封装；
- 模型厂商 API 的调用代码；
- 文件上传、账号页面等通用 CRUD；
- 用户数据本身。

保护这些低复利代码只会降低信任和生态速度。真正应保护的是“如何稳定完成科研任务并持续提高质量”的系统。

## 7. 决策摘要

```text
开放：标准、接口、开发工具、基础运行时、导入导出、示例与兼容测试
共建：Skill、插件、模板、连接器、分类与市场信誉
保护：生产编排、证据质量、上下文编译、评估数据、组织治理和商业控制面
```
