# Scholar Harness 产品战略路线选择

> 建议选择：**当前聚焦 B「科研 Agent 平台/工作台」，以 A「AI 论文助手」作为获客切入口，并用架构逐步走向 C「科研 AI OS」；未来 18 个月不直接以“科研 AI OS”对外承诺。**

## 1. 三条路线定义

### 路线 A：AI 论文助手

围绕检索、综述、讨论、改写、引用和投稿交付，让个人用户快速完成论文相关任务。

### 路线 B：科研 Agent 平台/工作台

围绕科研项目，把文献、PDF 证据、数据、分析、图表、写作、工具和任务状态统一编排，支持个人与实验室扩展。

### 路线 C：科研 AI 操作系统

成为科研数字工作的底层平台，统一资产、应用、权限、Agent、计算、协作、治理和生态标准。

## 2. 评估标准

- 用户问题是否高频、紧迫且愿意付费；
- 是否与现有能力匹配；
- 能否建立差异化与长期壁垒；
- 能否从个人扩展到 Lab/Enterprise；
- 团队能否在 12–18 个月内可靠交付；
- 是否会被基础模型能力快速吞噬；
- 是否容易形成清晰的市场表达和增长入口。

## 3. 路线评分

评分为 1–5，代表当前阶段的相对适配度。

| 维度 | A 论文助手 | B Agent 平台 | C 科研 AI OS |
|---|---:|---:|---:|
| 用户需求清晰度 | 5.0 | 4.2 | 2.8 |
| 当前产品匹配度 | 4.0 | 4.6 | 2.8 |
| 短期变现 | 4.4 | 4.1 | 2.2 |
| 差异化空间 | 2.8 | 4.6 | 5.0 |
| 机构扩张 | 2.5 | 4.7 | 5.0 |
| 实施可控性 | 4.3 | 3.8 | 2.0 |
| 抵御模型平台挤压 | 2.4 | 4.3 | 4.7 |
| 综合判断 | 3.8 | **4.4** | 3.5 |

## 4. 为什么不是只做路线 A

路线 A 最容易被理解和获客，但存在明显问题：

- 生成、改写、总结会被基础模型快速商品化；
- 单次论文任务留存有限，容易陷入价格竞争；
- 用户只把产品当作聊天工具，无法理解 PDF Wiki、数据分析和任务恢复的价值；
- 难以承载实验室与机构的治理需求。

但 A 仍然应保留为增长楔子。对外入口可以是“有证据的论文写作”，进入后逐步让用户采用项目、证据库、分析和复用能力。

## 5. 为什么现在选择路线 B

路线 B 与当前真实代码和能力最匹配：

- 已有两级 Agent、统一聊天、Skill/MCP 与本地工具；
- 已有 Embedding 文献库、PDF Wiki 和混合检索；
- 已有 Auto Research、文献计量、Meta、R/Python 和 Office 工作流；
- 已有 Electron 本地优先形态、云端账号/授权和插件管理；
- 已出现构造 Agent、能力清单和权限治理的雏形。

这些能力已经超过传统“论文助手”，但尚未达到操作系统级别的稳定性、标准化与生态规模。因此最真实的定位是“科研 Agent 工作台/平台”。

## 6. 为什么暂不把路线 C 当作市场承诺

“操作系统”意味着：

- 稳定的公共能力模型与开发者接口；
- 统一资产 schema、身份、权限和事件系统；
- 可验证的扩展生态与兼容性；
- 机构级治理、审计、部署和服务保障；
- 足够大的开发者和合作伙伴网络。

SH 目前具备方向性雏形，但还存在前端单体、路由分散、恢复行为不一致、许可证未统一和工作流可靠性等工程债。过早宣传 OS 会提高用户预期、分散资源并降低可信度。

## 7. 建议的三层产品叙事

### 市场入口

> 有证据、可追溯的 AI 论文与科研助手。

用户无需先理解平台，即可从写作、PDF、Meta 或数据分析进入。

### 当前产品身份

> 本地优先、证据驱动、可扩展的科研 Agent 工作台。

强调跨工作流任务完成、研究资产复用和工具连接。

### 长期架构愿景

> 面向个人与科研组织的开放科研 AI 操作层。

“操作层”比立即宣称“操作系统”更准确，也给未来 OS 化保留空间。

## 8. 三阶段路线图

### 阶段 1：可信任务工作台（0–6 个月）

目标：把“能做很多事”变成“3 件关键事稳定完成”。

- 灯塔工作流 1：句子级证据检索、引用核验与写作；
- 灯塔工作流 2：PDF → 证据资产 → 项目复用；
- 灯塔工作流 3：Meta/数据 → 统计分析 → 图表与报告；
- 统一执行内核、状态恢复、产物登记与质量评估；
- 上线清晰 Free/Pro 权限与成本管理。

### 阶段 2：科研 Agent 平台（6–18 个月）

目标：形成扩展生态和实验室复用。

- Research Asset Graph；
- 统一 Skill/MCP/连接器 SDK、注册表与质量门禁；
- Lab 空间、模板、权限、审计和团队资产；
- 与 Zotero、Office、R/Python、公开数据库深度连接；
- 通过真实工作流评估持续提升质量。

### 阶段 3：科研 AI 操作层（18–36 个月）

目标：成为机构科研 AI 的标准入口。

- 开放资产与能力标准；
- 多模型、多计算环境和私有数据连接；
- 企业策略、合规、审计与部署控制面；
- 第三方应用和工作流市场；
- 合作伙伴和机构标准网络。

## 9. 路线边界

### 应该做

- 把模型、文献、数据、工具和规则编排成可靠任务；
- 建立证据、引用、数据与产物的可追溯关系；
- 支持本地优先和模型中立；
- 让个人资产自然扩展到实验室标准流程；
- 用开放规范扩大生态，用私有内核保证质量与商业化。

### 现在不做

- 通用办公套件或 Notion 替代品；
- 自研基础大模型；
- 无边界的浏览器自动化和反验证码工具；
- 每个用户需求都写入核心的重定制；
- 在没有稳定公共 API 和生态前宣传完整 OS。

## 10. 路线决策门禁

每个新功能必须回答：

1. 它是否提升至少一个灯塔工作流的成功率或质量？
2. 是否生成或复用 Research Asset Graph 中的资产？
3. 是否可以通过 Skill、插件或配置实现，而不是污染核心？
4. 是否有可测量的用户结果与维护负责人？
5. 是否符合数据、许可、成本和商业边界？

不能满足上述问题的功能原则上不进入核心路线图。

## 11. 最终选择

> **战略选择 B，增长使用 A，架构通向 C。**

- 用论文与证据任务获取个人用户；
- 用科研 Agent 工作台建立留存与付费；
- 用资产图谱、开放标准和组织治理逐步形成科研 AI 操作层。

这样既利用当前产品的真实优势，也避免过早承担“科研 AI OS”的全部承诺。
