# Scholar Harness 创始人战略建议

> 最重要的建议：停止用“新增多少功能”衡量进展，开始用“多少关键科研任务能够稳定、可信、可恢复地完成”衡量产品。SH 已经不缺能力入口，当前最稀缺的是收敛、可靠性、证据质量和商业边界。

## 1. 创始人必须做出的八个决定

1. **产品身份**：当前是科研 Agent 工作台，不是通用聊天工具，也暂不对外宣称完整科研 AI OS。
2. **增长楔子**：以证据驱动的论文写作、PDF 证据库和数据/Meta 分析获客。
3. **北极星指标**：每周被用户接受、具备来源与产物的科研任务完成数。
4. **灯塔工作流**：未来半年只把 3 个端到端工作流做到行业领先。
5. **开源边界**：开放标准、SDK 和轻量运行时；保护生产内核、评估、组织治理和商业控制面。
6. **数据原则**：用户研究数据归用户；任何训练或质量使用均需明确授权。
7. **商业路径**：Free→Pro→Lab→Enterprise，不以字符包和终身无限作为长期产品架构。
8. **组织纪律**：新功能必须通过价值、架构、质量、维护和商业五项门禁。

## 2. 未来三年不要做什么

### 2.1 不要做通用办公平台

不要试图替代 Word、Notion、浏览器、Zotero、Excel、RStudio 或完整 IDE。连接并编排它们比复制它们更有价值。

### 2.2 不要参与基础模型军备竞赛

不自研通用大模型，不把品牌绑定单一模型。持续保持模型中立，把竞争力放在科研上下文、证据和执行质量。

### 2.3 不要让每个用户需求进入核心

大量个性需求应通过配置、Skill、插件或构造 Agent 的隔离功能包实现。进入核心必须证明对灯塔工作流有普遍价值。

### 2.4 不要用“所有功能免费”换增长

免费层负责体验和生态，复杂执行、可信质量、资产规模和组织治理必须付费，否则成本和支持会吞噬产品。

### 2.5 不要依赖无限终身套餐

模型、存储和支持是持续成本。终身权益只能覆盖明确的本地软件能力，不能承诺无限云端计算与服务。

### 2.6 不要把用户资料当作默认训练数据

论文、实验数据和未发表结果高度敏感。必须最小化采集、明确授权、支持删除与导出，并给机构提供数据边界。

### 2.7 不要绕过出版商、数据库或验证码规则

连接器必须遵守许可、登录和访问条款。浏览器辅助用于合法交互与用户确认，不用于规避反爬或访问控制。

### 2.8 不要让 UI 微调持续打断核心工程

视觉品质重要，但应通过设计系统、组件和验收标准批量解决，避免每个像素需求直接修改共享单体代码并影响聊天、PDF、Meta 等模块。

## 3. 必须优先做什么

### P0：统一执行内核

- 主页、Meta、计量、PDF 和专用聊天使用同一任务模型；
- 统一意图、上下文清单、工具路由、状态、取消、恢复和产物登记；
- 页面关闭、GPU 崩溃或重启后能重连原任务；
- 禁止同一任务出现重复日志气泡和重复执行。

### P0：证据与质量系统

- 建立句子、论点、文献、摘要、引用和尾注的稳定关系；
- 对检索、引用支撑、Meta 数据和统计输出建立测试集；
- 每次发布运行端到端回归，不以“AI 看起来回答了”作为成功；
- 对不确定结果明确标记，不制造虚假引用或完成状态。

### P0：上下文与成本治理

- 默认只发送清单、摘要和路由信息；
- Agent 按需读取 Skill、MCP、文件、历史和检索结果；
- 建立上下文缓存、版本和 token 预算；
- 把重复的超大 Prompt 当作产品缺陷处理。

### P1：Research Asset Graph

- 给项目、文献、PDF、句子、数据、分析、图表、草稿和产物统一身份；
- 记录来源、版本、权限和生成血缘；
- 支持跨工作流复用和完整导出；
- 为 Lab 共享和审计打基础。

### P1：产品与商业权限

- 保持月度、季度、年度软件订阅不限制字符数；未来差异化只围绕任务能力、协作规模和治理权益；
- 完成 Free/Pro 权限、成本和转化埋点；
- 用 5–10 个实验室共创 Lab，不先做大而全企业定制；
- 明确模型费用、自带 Key 和 SH 服务费的关系。

### P1：开源与生态治理

- 维护已落地的根许可证，并继续补齐第三方许可清单；
- 划分开源、社区和私有核心仓库；
- 建立扩展 manifest、权限、测试、签名、升级和卸载；
- 先做 20 个高质量官方扩展，再追求市场数量。

## 4. 建议的资源分配

在现阶段团队资源有限的情况下：

| 方向 | 建议占比 | 目标 |
|---|---:|---|
| 执行内核、可靠性、恢复、性能 | 30% | 任务不丢、不重、不假完成 |
| 证据、检索、评估和资产图谱 | 25% | 形成专业质量与数据壁垒 |
| 核心产品体验、onboarding、Pro | 20% | 提高激活、留存和付费 |
| 开源标准、扩展生态 | 10% | 扩大能力与分发 |
| Lab、权限、安全和部署 | 10% | 验证组织商业化 |
| 探索性功能 | 5% | 受控实验，不污染核心 |

如果当前团队更小，应优先砍掉探索项，而不是压缩可靠性和质量。

## 5. 最大风险清单

### 风险 1：产品碎片化

表现：主页、Meta、计量、PDF 各有聊天、上下文、恢复和文件逻辑；修改一处影响多处。

措施：统一执行内核和公共组件；专用页面只提供上下文和展示，不复制 Agent。

### 风险 2：可信度事故

表现：错误引用、假 DOI、证据不支撑、任务显示完成但文件不存在。

措施：证据结构化、文件存在性校验、发布评估、失败显式化和审计日志。

### 风险 3：上下文和模型成本失控

表现：数十万 token Prompt、重复历史、启动慢、空响应与超时。

措施：动态上下文库、按需读取、缓存、模型分层、任务预算和成本指标。

### 风险 4：许可与数据合规

表现：根许可证缺失、第三方代码来源混乱、数据库采集越界、敏感数据处理不清。

措施：开源法律清单、SBOM、数据政策、来源许可、企业数据处理协议。

### 风险 5：创始人和单体代码的关键人风险

表现：产品知识集中、持续热修、缺乏可回归标准。

措施：架构决策记录、模块负责人、自动测试、发布清单、设计系统和故障复盘。

### 风险 6：机构定制吞噬产品

表现：每个客户一套分支，收入增长但毛利和迭代速度下降。

措施：只接受可配置、可插件化、可复用的需求；定制价格覆盖长期维护。

### 风险 7：基础模型平台挤压

表现：普通写作和文件工具被模型原生能力替代。

措施：把品牌和收入移向证据质量、资产复用、组织治理和跨工具任务完成。

## 6. 90 天行动计划

### 第 1–30 天：收敛与立规矩

- 定稿定位、产品边界和三条灯塔工作流；
- 设立北极星指标、质量指标和成本指标；
- 确定开源许可证、私有核心和用户数据政策；
- 冻结非关键核心功能新增；
- 为统一执行内核和 Research Asset Graph 写 ADR。

### 第 31–60 天：可靠交付

- 让三条灯塔工作流通过端到端测试；
- 统一取消、恢复、日志、文件和历史会话行为；
- 上线上下文预算和 Prompt 诊断；
- 建立 50–100 个高风险科研任务评估样例；
- 完成 Free/Pro 能力矩阵和事件埋点。

### 第 61–90 天：验证商业与生态

- 向真实用户发布 Pro；
- 招募 5–10 个 Lab 设计伙伴；
- 发布公共 schema、SDK 预览和 20 个官方扩展；
- 建立周度质量、成本、留存和转化复盘；
- 对 90 天没有使用或无法证明价值的功能降级为插件或移除。

## 7. 未来 12 个月的公司级 OKR 建议

### O1：成为可信科研 Agent 工作台

- KR：三条灯塔工作流任务成功率达到可定义且持续提高的目标；
- KR：严重引用/文件错误率低于设定阈值；
- KR：任务恢复成功率和 30 日留存达到目标；
- KR：上下文 token/完成任务下降而接受率不下降。

### O2：建立可持续个人商业模式

- KR：Free→Pro 转化达到可持续获客成本要求；
- KR：Pro 毛利覆盖模型、存储和支持；
- KR：年度订阅成为主要个人收入，而非终身套餐；
- KR：至少一个灯塔工作流成为明确付费原因。

### O3：验证 Lab 扩张

- KR：5–10 个设计伙伴持续使用；
- KR：团队资产复用、模板和审计产生可量化价值；
- KR：完成标准化 onboarding、权限、部署和支持手册；
- KR：Lab 合同不依赖专有代码分支。

### O4：建立开放生态基础

- KR：根许可证、SDK、manifest、测试与签名规范公开；
- KR：20 个官方扩展稳定运行；
- KR：出现外部维护者和有效贡献；
- KR：扩展驱动的任务量占比持续上升。

## 8. 功能立项检查表

任何功能立项前必须写清：

- 用户是谁、要完成什么任务、当前损失是什么；
- 它属于核心、官方插件、社区扩展还是服务；
- 是否复用统一执行内核和资产图谱；
- 成功、失败、取消和恢复如何定义；
- 会读取什么数据、调用什么权限、产生什么文件；
- 如何测试、监控、升级、卸载和回滚；
- 谁维护，三个月后用什么数据决定保留或删除；
- 如何提升留存、付费、质量或生态，而不是只增加展示效果。

## 9. 何时进入 Enterprise

只有满足以下条件再规模化：

- Lab 产品已经在多个团队稳定使用；
- 核心工作流和权限模型标准化；
- 有部署、升级、监控、备份和审计方案；
- 支持成本和毛利有清晰模型；
- 企业需求可配置化，不需要长期维护客户分支；
- 具备合同、隐私、安全和第三方许可基础。

## 10. 创始人应亲自保护的资产

- 产品边界和路线纪律；
- Research Asset Graph 和执行内核的架构一致性；
- 证据质量标准、评估集和发布门禁；
- 用户信任、数据权利和学术诚信；
- 开源与私有核心边界；
- Lab 设计伙伴关系和关键生态合作；
- 对“什么不做”的最终决定权。

## 11. 一页结论

1. SH 已经具备科研 Agent 平台的能力广度，但尚缺把广度转化为稳定价值的统一内核。
2. 未来半年不应继续以入口数量扩张，而应把三条灯塔工作流做到可信、可恢复、可评估。
3. 论文助手是入口，科研 Agent 工作台是当前身份，科研 AI 操作层是长期愿景。
4. 真正的长期资产是科研资产图谱、执行内核、证据评估、生态标准和组织治理。
5. 开源用于建立标准与生态，私有核心用于保证生产质量和商业可持续。
6. 用户数据归用户；增长不能建立在默认收集敏感研究内容之上。
7. Free/Pro 先验证个人价值，Lab 验证扩张，Enterprise 等标准产品成熟后再规模化。
8. 创始人最大的任务不是继续加功能，而是建立边界、指标、质量纪律和可复制组织。
